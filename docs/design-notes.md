# 设计说明

这份文档解释 `req` 为什么长成现在这样。想看怎么用，回 [README](../README.md)；想改，看 [CONTRIBUTING](../CONTRIBUTING.md)。

## 一、它到底在防什么

`req` 的每一条规则几乎都能对应到一个具体的失败模式。列出来，改规则的时候才好判断能不能删。

| 失败模式 | 对应规则 |
| --- | --- |
| 用户只说零散困扰，Agent 未整理含义就判断任务范围 | §1 先增强提示词，区分原意、AI 可能理解和关键缺口，再判断是否需要访谈 |
| 用户一句"做个记账工具"，Agent 立刻开始设计表结构 | §1 关键需求未明确前不输出实现任务表、不锁技术架构、不宣布开始开发 |
| 一次甩 20 个问题，用户被劝退 | §3 每轮只问 1—3 个独立决策，不能一题里塞十个子问题 |
| Agent 自导自演，把沉默当默认同意 | §3 提问后等真实回答；不能自问自答，不能把沉默、超时或默认勾选当成同意 |
| 反复问用户已经答过的事 | §2 禁止重复询问已经回答过的问题 |
| 把 AI 自己加的功能算进承诺范围 | §7 不把 AI 新增的想法混进承诺范围 |
| 用户说"随便"，Agent 就当拿到授权去删数据 | §5「随便／你看着办」不是代付费、公开数据、扩大访问权或永久删除的授权 |
| 说"需求成熟度 95%"这种没法验证的话 | §7 不使用虚构的成熟度指标，改为 7 条可检查的条件 |
| 需求没确认就开始写代码 | §8 确认需求 ≠ 确认开发计划，更不等于授权执行有风险的操作 |
| 偷偷把功能删掉来宣布"需求已经清楚了" | §7 可以通过排除功能解除阻塞，但必须拿到对范围变化的确认 |
| 把架构图当成技术选型结论 | §6 需求层面的模块与数据流概览，不提前锁定技术栈、数据库产品、部署方案 |

## 二、双版本差异对照

两份 `SKILL.md` 是同一套规则的两种宿主表述。**除下表四处外逐字一致**，这不是疏漏，是刻意设计。

| 位置 | `req-workbuddy` | `req-openai` | 为什么 |
| --- | --- | --- | --- |
| frontmatter `description` | 写明"通过 WorkBuddy 原生选择弹窗分轮追问" | 写为"通过分轮追问" | `description` 是隐式匹配的依据，写死宿主专属能力会让另一个平台匹配失准 |
| §3 小节标题与正文 | 「提问一律用 AskUserQuestion」，工具**唯一指定** | 「提问优先用宿主的原生提问工具」，无工具时降级为普通提问 | WorkBuddy 保证有这个工具，可以硬要求；Codex 侧不保证，必须留降级路径 |
| §8 确认方式 | 明确用 `AskUserQuestion` 收集范围反馈 | 写为"宿主的结构化提问工具（没有则普通提问）" | 同上 |
| §9 模式切换 | 「由用户在 WorkBuddy 里自行切换」 | 「由用户自行在宿主中切换」 | 纯措辞 |

`assets/icon.svg` 两版完全相同。

**唯一指定**和**优先使用**是这次区分的关键词，别改混了：前者是硬约束（工具在就必须调），
后者是软优先级（有就用，没有就降级）。把 WorkBuddy 版的"唯一指定"改成"优先使用"，
弹窗提问会退化成正文里列 A/B/C——这正是 §3 明确禁止的行为。

## 三、几个刻意的取舍

### 为什么先增强提示词，再判断范围

用户可能只说「月底数字老对不上」，尚未把目标、场景和期望结果表达完整。先把这些线索整理出来，
再提出与原话有关的可能理解，能给后续判断和提问提供更清楚的起点。

增强内容直接融入首轮 1—3 句话的复述，不额外增加审批。原话和明确限制始终保留；可能理解记为
「AI 建议」，缺口记为「待决定」，不能因 AI 写出了完整句子就认定需求已经清楚。明确的小修改只做
简短整理，用户要求不改写时遵从。第 2 节继续调查项目并更新同一份决策记录。

### 为什么不用"需求成熟度百分比"

任何百分比都是编的，而且不可反驳——Agent 说 90% 你没法说它是错的。`req` 换成 7 条勾选条件，
每条都能对照检查"过了没有"。**可验证性优先于好看的数字。**

### 为什么把"谁来决定"单独成节（§5）

需求访谈最容易出的事故是**越权代替用户决策**。目标、范围、权限边界、费用、数据用途、
不可逆操作——这些必须用户拍板；Agent 只承担"能从代码查明的事实"和"不改变上述决定前提下的技术建议"。
技术选择一旦影响费用、部署方式、数据出境或维护负担，也必须先把后果讲清楚再让用户选。

### 为什么决策记录只有五种状态

`用户已确认 / 证据已核实 / AI 建议 / 待决定 / 暂不做`

因为一份需求里最危险的混淆，是**把"AI 建议"和"用户已确认"当成一回事**。
这两种状态在后续开发里的分量完全不同，必须在记录层面就分开。
架构图上的"待确认"和"AI 建议"标注，也要和这份记录对得上——不能只靠颜色区分。

### 为什么图示不锁技术栈

需求阶段的架构图回答的是"有哪些模块、数据怎么流"，不是"用什么框架、什么数据库"。
提前锁死会做两件坏事：让用户以为技术方案已经定了；让真正该在计划阶段做的技术比较失去空间。

### 为什么放弃"接管全生命周期"

`req` 到需求确认就停，不做任务拆分、不写代码、不做测试、不审查代码。
不是不能做，是**做了就越权**——需求确认和"可以开工"是两回事，中间还差一次开发计划确认。

## 四、它不保证什么

说清楚边界，比多列几条功能重要：

- 它是**工作流约定，不是强制拦截器**。没有权限系统兜底，靠的是宿主自身的指令优先级。
- 它**不会自动切换计划模式**，只会在结束时提示你"需求已可用于计划"。
- 它**不读记忆目录**。需求简报和图文件是交付物，不是助手自己的笔记。
- 宿主限制导致图或文件没存成时，它应当**如实说明未保存**——这不是缺陷，是设计要求。
  一个声称"已保存"但实际没写的技能，比一个承认失败的技能危险得多。

## 五、术语

| 词 | 含义 |
| --- | --- |
| 需求简报 | 访谈的正式产出，模板见 `SKILL.md` §8 |
| 收口标准 | §7 的 7 条可检查条件，全过才算需求清楚 |
| 阻塞缺口 | 影响业务、权限、费用、数据或不可逆行为的关键未决项 |
| 待决策草稿 | 用户要求停止提问、但仍有阻塞缺口时的简报状态，不得冒称已确认 |
| 可进入计划 | 需求状态标记，仅表示需求清楚，不代表已授权开工 |
